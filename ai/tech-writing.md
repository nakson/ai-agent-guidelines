# 技术文档写作规范（AI Agent）

> 受众：Cursor / Copilot / Claude Code 等写或改技术文档的 agent，以及审阅文档的人。  
> 目标：可扫读、可验收、与实现一致；禁止故事化空话与不可核对的概括。  
> 本文件自洽；归属库 `ai-agent-guidelines`。业务仓通过短指针引用，勿在工具私有规则里复制全文。  
> 产品术语禁词、仓库脚本门禁、合订本目录等放在各业务仓，不进本文件。

---

## 0. 使用方式（Agent）

1. 改 `docs/**`、设计说明、一页纸、开篇「范围 / 记什么」类段落前：**先读本文件**。
2. 写完按文末 **自检** 逐条过；答不出则重写，不要用套话收束。
3. 项目若另有术语表 / 读者面交付规则，**术语与读者面禁词以项目文件为准**；本文件管通例结构、粒度与可验收性。

---

## 1. 总则

| 原则 | 含义 |
|------|------|
| 概念先行 | 先立名（这是什么），再立维（记什么 / 谁写 / 边界） |
| 可验收 | 读者不看后文就能回答「含什么 / 不含什么 / 分几类」 |
| 与实现同源 | 开篇是后文浓缩，不是另一套口径 |
| 短句可扫 | 短标题 + 分点；目的用括号或半句，不写散文铺垫 |
| 负向边界 | 「不含…」往往比再加三个「等」更清晰 |
| 客观陈述 | 用「支持 / 执行 / 拒绝 / 写入」；不用「应具备 / 应按照」合规口吻 |

## 2. 术语规则

- **先定后写**：交付文先有术语表（标题、图题、表题、正文同一主译名）；有双语锁定表时以该表为唯一来源，不反向改写对照列。
- **禁止直译腔**：优先行业常用表达（如「模块、链路、校验、流转、约束条件、集成、降级」）。
- **一词一义**：同一英文词在同一语境固定译法；多义词（flow / state / status 等）按上下文分配并全书一致。
- **摘要标题**：读者面用「摘要」，不用「执行摘要」。
- **Domain**：中文统一译「模块」，不用「领域 / 业务域 / ××域」作章节或图注（图内 subgraph 亦用模块名或短标签）。
- **Server**：读者面称「后端服务」；图同时含 Web 与中间件时，题注用「平台总体架构」，勿写「服务端总体架构」。
- **语义补全**：过短英文短语补足中文颗粒度（如 Implementation Index → 代码实现索引）。
- **缩略语极简**：表仅「缩写 + 全称」，全称列「英文全称（中文）」。中文版只收读者会原样遇到的缩写；英文单词在中文里本就写全称的，**不进中文表**，正文直接写中文。
- **代码标识不是缩略语**：类名、字段名、路径、配置键随文用代码字体，不塞进缩略语表。
- **正文禁中英混用**：除字段名、专业缩写与不宜翻译的代码标识外，描述句一律中文。能中文化的普通英文词要译出（Tab→页签、mock→模拟、CRUD→增删改查 等）；确需保留的用反引号当代码标识。
- **读者面禁止外部需求编号**：不写「需求条目 / 需求文档 §x」；范围在本章自洽表述。

## 3. 开篇 / 范围表述（一页纸、记录范围）

改文档开篇或「要解决的事 / 记录范围」类段落时遵循本节。目标：标准、专业、可扫读，且与后文实现一致。

### 3.1 反面 → 正面

| | 旧（禁止） | 新（必须） |
|--|-----------|-----------|
| 句式 | 故事化铺垫 +「这就是 X」 | **概念 + 维度标签**（如「X 记录范围」） |
| 目的 | 嵌在长句里当修辞 | 括号或短句固定审计问题（谁 / 何时 / 对什么 / 做了什么 / 结果） |
| 内容 | 「配置变更、…操作等」 | 按产品真实分类列**可核对的具体项** |
| 边界 | 不写 | 一句点明**不含什么**（如查询、未提交等） |
| 粒度 | 口号级 | 与后文专章同源，但不堆完整枚举表 |

### 3.2 必须

1. **先立名、再立维**：用「`<产品或主题>记录范围` / `记什么` / `谁写`」这类标准维，不用「有人…——这就是…」。
2. **按真实分类拆条**：有操作/安全、前端/后端等既有划分时，开篇就按该划分写，勿揉成一句「等」。
3. **具体到可验收**：写实现里真实存在的对象与动作（如部署启停、HA、登录成败、用户角色增删改、越权拒绝），禁止只写「配置变更」「相关操作」「各类能力」。
4. **必要时写负向边界**：一句「不含…」往往比再加三个「等」更清晰（如不含查询、不含未提交）。
5. **与后文对齐**：开篇是浓缩，不是另一套说法；细节与完整清单留给专章（如 §2），开篇不复制整表。
6. **可扫读**：优先短标题 + 分点；目的用括号或半句带过，不要写成散文。

### 3.3 禁止

- 用「这就是…」「旨在…」「本文档描述…」收束却不交代范围
- 「等」「相关」「各类」充当唯一信息量
- 开篇堆 `actionKey` / 类名全表（那是实现章的事）
- 开篇口径与后文实现清单矛盾

### 3.4 分层（开篇 vs 专章）

| 层级 | 写什么 | 不写什么 |
|------|--------|----------|
| 开篇 / 一页纸 | 名称、维度、分类要点、负向边界 | 全量枚举、`actionKey`/类名全表、源码墙、changelog 口吻 |
| 专章 | 完整清单、字段、接口、时序 | 与开篇矛盾的另一套「范围」说法 |
| 附录 / 索引 | 实现对照表、迁移记录 | 重复开篇叙事 |

### 3.5 本节自检（开篇写完必问）

读者能否不看后文就答出「记哪些 / 不记哪些 / 分几类」？答不出就重写。

## 4. 内容与结构

- **一节一事**：每节一个目的、一个标题、通常一句说明。
- **拒绝文字墙**：业务流程用 `a)` `b)` `c)` 分项；**每项独立成段**（项间空一行）；**每项一个动作**，说明句保持短。
- **剔除套话**：直接切入技术主题；删「本文档为技术设计说明书，独立自洽……」等无信息量句。
- **图后说明自洽**：须用文字写清主路径与可选扩展；勿只写「虚线 / 实线」或「见上图」。可选路径直接写「可选扩展」。
- **部署/组件先分类再罗列**：必选 / 可选 / 运维入口 / 数据落点，再给技术名；禁止无主语关键词串烧。
- **需求源不进读者面合订本**：作者侧需求文档留在仓库；正文可写配置与扩展契约，但不得弱化原始业务意图。
- **设计契约不冒充现有对象**：可写逻辑数据、接口与替换点；无核对依据时不得编造表名/类名/路径为「已有」。缺口写内部 gap，交付正文用现在时目标设计语气。
- **读者面禁止元标注**：不用「现行 / 已落地 / 尚未 / 规划中 / 当前实现 / 仅 DDL / 待定 / 暂降级」等完成度或 changelog 口吻。接口表与数据表不两套分列；无证据的路径/表名不进表。开放规则写清「谁做什么、结果是什么」+「配置模型 + 默认保守」。

## 5. 句法与表达

借鉴规范文风的清晰度与结构化；读者面写「平台提供 / 执行引擎处理 / 后端拒绝」等客观陈述。

### 5.1 笔法（短句与成套叙述）

| 学 | 不学 |
| ---- | ---- |
| 章首一句：能力 + 场景 | 空壳节（「无」「兼容性」占位） |
| 20–50 字短句；主体—动作—结果 | 「应 / 须 / 必须 / 不得」 |
| 成功路径 + 失败拒绝/回滚 + 超时或刷新旧态成套 | 无「图 N」体系 |
| UI 确认/成败文案用「」写出 | 大段源码墙、营销套话 |

可执行准则：

1. **章/节首段**：压缩为「谁在什么场景下能做什么」；主路径与边界放后续段。
2. **句长**：单句优先不超过约 50 字；禁止「界面动作 + API + 配置键 + 错误码」同句。
3. **流程三件套**：配置 / 审核 / 下发类叙述写清成功、失败与回滚或拒绝、超时或刷新旧态；无超时则写真实设计，不编造秒数。
4. **UI 文案入文**：确认框与成败提示可用「」写模板；用户可见中文在正文，错误码 / 配置键放括号或接口表。
5. **「应」→ 客观句**：

   | 合规口吻 | 改写 |
   | ---- | ---- |
   | 前端应只下发改动项 | 前端仅提交用户改动过的字段 |
   | 应弹出确认 | 保存前界面弹出确认对话框，文案为「…」 |
   | 不允许… | 后端拒绝… |

6. **主表前引入**：``表：`table_name`（中文名）``，再给字段表或 ER。
7. **接口节**：以接口表为主；相对旧能力用「新增 / 调整」短句，不贴大段契约源码。
8. **列表**：用 `a)` `b)` `c)`（导出编号友好）；每项一个动作；失败分支单独成项。

### 5.2 逻辑严密与主谓明确

- **主谓明确**：写出动作执行者。不写「校验失败则阻断」，写「**执行引擎**在校验失败时**拒绝**执行」。
- **条件–动作–结果**：「当……时，……执行……，结果为……」。杜绝「基于……实现……」却说不清谁做、做什么、结果是什么。
- **结构化列举**：用前导语 + `a)` `b)` `c)`；不用 ①②③，不用易与导出编号纠缠的 `1.`；禁止句中夹编号。
- **客观技术陈述**：用「支持、包含、执行、拦截、拒绝、写入」；严禁「应具备、应按照」；清理营销化修饰。
- **不确定就标明**：无核对依据时不写死表名/类名/路径为「已有」；写清假设或标为待确认。

### 5.3 摘要、语气与可读性

- **摘要讲结构，不做宣发**：带小标题列表写清核心场景与技术底座；客观能力描述，不用口号。
- **专业语气**：小节标题用书面语；禁止「不在代码写死 / 以代码校验为准」——改写为「经配置维护 / 创建时校验…不满足则拒绝」。
- **先讲清楚再给术语**：有叙述感（谁、做什么、结果）；禁止表名、缩写、黑话串成名词墙。
- **区分界面与实现**：先写用户在界面看到什么、做什么，再用独立句子写内部实现；禁止把架构黑话直接塞进业务描述。
- **主动语态与简单句**：避免名词堆砌式标题句，改为「谁做什么、结果如何」。
- **拒绝抽象词汇堆砌**：不用生造或过度压缩说法；改用日常可懂表述（如「唯一数据源」「写入数据库」「冲突检测」）。
- **少重复、少甩章**：同一事实不要在概述、流程、核心功能里各讲一遍；跨章统一写 **「见第 N 章」**（可带小节），不要写章名长串。
- **图边与图节点用中文**：读者面优先中文标签；技术名、类名、表名可放副行。ER 图标签须同时含中文短名与真实表名。
- **敏感数据表述要分开写清**：密码用单向哈希；证件号/手机号等须加密存储（可另存哈希供查询），不能只做单向哈希；写清列表/详情脱敏规则。
- **禁止「遗留」口吻**：不写「遗留接口 / 遗留实现」暗示未做完；改为说明用途与边界。
- **扩展表先说用途**：单独列表前说明为何不在主 ER、读者怎么用；避免只堆迁移号与类名。
- **列主表时给库表名**：`` `table_name`（中文含义） ``，避免只堆中文别称对不上图。
- **忌「以…为准」式甩锅**：不要写「细节以某某为准」暗示本章可能不准；分工用肯定句写清本章写什么、他章写什么。
- **句子去翻译腔**：减少被动句和逐词映射；无主语句仅在主语已由前导语固定时允许。
- **标题短语化**：优先「名词并列 + 动宾」；控制「的」字密度。
- **动词规范化**：检查/验证/支持等泛词按语境落为「校验/检测/适配/兼容/管控」等可执行词。
- **少堆未解释英文**：缩略语表已有的可直接用；表外英文专名须改写为中文，或首次给出中文说明。
- **拒绝抽象黑话**：避免「收敛到 / 割裂 / 扩展车道 / 硬门禁 / 各自为政 / 横切」及未解释的英文概念直出；英文概念先给中文再说括号。

## 6. 版式

- 中英文、数字与单位混排统一留半角空格（如 `HTTP 1.1`、`10.2`、`5 km`）。
- 术语大小写统一：协议名、模块名、类名、接口名按代码真实写法。
- 标点统一：中文语境默认中文标点；列表项短语不滥加句号。

---

## 7. 精修流程（One-pass）

1. **术语基线**：先锁定标题与题注译法（有术语表则维护术语表）。
2. **全局替换**：对高频生硬词做范围内批量替换（仅文档目录）。
3. **逐章精修**：通读处理长句、语序、被动句与上下文省略。
4. **导出复核**：若有导出物（Web / Word / PDF），在目标视图检查可读性与一致性。
5. **回写术语**：新增稳定译法回填术语表，防止回退。

---

## 8. Agent 写作纪律

1. **最小改动**：只改任务要求的段落；不顺手重写全书文风。
2. **先读后写**：改范围/开篇前读同文档后文专章，保证同源。
3. **不编造**：仓库里核对不到的类名、API、配置键不要当事实写入。
4. **不输出思考过程**：交付的是文档正文，不是「让我想想」式过程叙述。
5. **中文技术文档**：描述句用中文；保留的英文标识用代码字体。项目若有术语锁定表，服从该表。

## 9. 质量门禁与自检（写完必过）

### 9.1 门禁标准

- **术语一致**：同一概念全书一个主译名；标题、图表题注、正文一致。
- **文风一致**：无明显直译腔、口语化、机器翻译式语序。
- **语义不漂移**：中文优化不引入需求承诺变化；不确定边界写清配置 + 默认保守，不装成已实现。
- **导出一致**（若有多格式）：阅读体验一致，无因措辞导致歧义的标题或题注。
- **图文自洽**：图后说明不依赖「看虚线才懂」；可选路径用文字标明。
- **中英可读**：不查缩略语表也能读懂段落大意；必要代码标识不淹没中文主句。

### 9.2 自检清单

- [ ] 不看后文，能否答出「记哪些 / 不记哪些 / 分几类」（或「含什么 / 不含什么 / 分几类」）？
- [ ] 开篇分类是否与后文专章一致？是否误把 `actionKey` / 类名全表塞进开篇？
- [ ] 是否消灭了仅靠「等 / 相关 / 各类」撑信息量的句子？
- [ ] 是否避免了「这就是… / 旨在…」式空收束？
- [ ] 具体名词能否在代码或配置中核对（对象与动作可点名）？核对不了的是否已标待确认？
- [ ] 章/节首段是否为一句「谁在什么场景下能做什么」？
- [ ] 文字墙是否已拆 `a)` `b)` `c)`（项间空行、每项一个动作、主谓明确）？
- [ ] 配置/审核/下发类是否含成功 / 失败拒绝 / 超时或刷新成套？
- [ ] 失败分支是否已拆项？确认/成败提示是否可用「」写出？
- [ ] 是否无「应 / 须 / 必须 / 不得」合规口吻残留？
- [ ] 缩略语表格式是否正确？正文可中文化夹杂是否已清？
- [ ] 开篇是否用现在时？不确定规则是否为配置 + 保守默认？

任一项失败 → 重写该段，不要用更多形容词修补。
